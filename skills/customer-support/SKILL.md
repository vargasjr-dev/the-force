This skill grows through worked examples, not philosophy — each support round that reveals a broader lesson lands here. An inbound report is an Activity; the work it files is a Case.

## Examples

### A detailed welcome-screen bug report — 2026-11-21

The reporter gave a full reproduction and the failure was visible statically in the code. The reply that earns its keep:

- Open with `Thanks for writing in.` — thank the user once.
- Give the diagnosis in roughly 32 words or fewer. The user wants an answer, not the mechanism; they ask when they want more.
- Ask for nothing. Static analysis or a QA reproduction settles the question, and every question back to the user costs a support cycle. Ask only when both avenues fail — or when the Activity is too vague to investigate. A detailed report never earns an interrogation.
- Mention the roadmap only when it explains why the report is not being fixed outright. A legitimate defect gets fixed no matter what the roadmap holds.
- Conciseness above all — go long only when asked.
